# Configuration Control Flow

Purpose
-------
This document records the control flow for the repository's configuration process: how runtime configuration is gathered, how the canonical proxy Caddyfile is rendered, validated and (optionally) deployed, and how the interactive installer/prober flows integrate with that rendering step.

High-level inputs / outputs
--------------------------
- Inputs
  - Environment variables (.env or exported): OPENPROJECT_HOST_NAME, RAILS_RELATIVE_URL_ROOT, APP_HOST, PROXY_* variables, etc.
  - `proxy/Caddyfile.template` — canonical gomplate template stored in the repo
  - Interactive config file: `scripts/installation_scripts/interactive_config.cfg`
- Outputs
  - Rendered Caddyfile (temporary, e.g. /tmp/caddyfile.* or /tmp/rendered_caddyfile)
  - Deployed Caddyfile inside running proxy container at `/etc/caddy/Caddyfile` (when deploying)

Key scripts & files
--------------------
- `proxy/Caddyfile.template` — canonical gomplate template for runtime Caddy config
- `scripts/deploy/render_caddy.sh` — authoritative renderer: gomplate -> validate (caddy adapt) -> atomic deploy into proxy
- `scripts/installation_scripts/interactive_config.sh` — interactive installer that drives config and calls the renderer
- `proxy/test/run_integration_test.sh` — integration prober: creates a temporary project and test proxy to validate configuration
- `proxy/test/prober.sh` — interactive wrapper for the prober
- `.env` or `interactive_config.cfg` — environment values used to render the template

Configuration control flow (rendered tree)
------------------------------------------
The following ASCII tree shows the typical control flow for a configuration/deploy operation.

CONFIGURATION_FLOW

```text
root
├─ (1) load env/config files
│  ├─ read `.env` (if present)
│  └─ read `interactive_config.cfg` (interactive installer)
├─ (2) canonicalize runtime keys
│  ├─ prefer `OPENPROJECT_HOST_NAME` over legacy `OPENPROJECT_HOST__NAME`
│  └─ ensure `RAILS_RELATIVE_URL_ROOT` is set (default `/`)
├─ (3) render template
│  ├─ locate `proxy/Caddyfile.template`
│  ├─ detect gomplate delimiters (`{{ }}` or `[[ ]]`)
│  ├─ run `gomplate` -> produce temp file `/tmp/caddyfile.XXXX`
│  └─ capture gomplate errors (parse errors, missing envs)
├─ (4) validate rendered Caddyfile
│  ├─ prefer `docker compose exec proxy caddy adapt --config - < /tmp/file`
│  ├─ else try local `caddy adapt --config /tmp/file`
│  ├─ else try `docker run --rm -i caddy:2 caddy adapt --config /host_root/tmp/file`
│  └─ handle validation failures (report and abort)
├─ (5) dry-run or deploy
│  ├─ if `--dry-run` -> print results and exit
│  └─ else atomically copy into running proxy container and reload
│     ├─ `docker compose exec -T proxy sh -c 'cat > /etc/caddy/Caddyfile' < /tmp/file`
│     └─ `docker compose exec -T proxy caddy reload --config /etc/caddy/Caddyfile`
└─ (6) post-deploy checks
  ├─ smoke test (curl the site path)
  └─ log collection on failure
```

Error modes & notes
-------------------
- Gomplate parse errors: usually caused by malformed template expressions (e.g. stray characters or comment spacing). Example: `template: ...:40: unexpected "/" in command`.
- Caddy syntax errors: when the rendered file contains Caddyfile constructs split over lines or misplaced braces; run `docker run --rm -i caddy:2 caddy adapt --config - < /tmp/file` to inspect.
- Missing tools: `gomplate` and `caddy` are required for strict validation. The renderer will fall back to containerized `caddy adapt` where possible.

How the interactive installer ties in
------------------------------------
- `scripts/installation_scripts/interactive_config.sh` collects configuration, computes derived values (like `RAILS_RELATIVE_URL_ROOT`), and calls the renderer (or validates generated files). It expects `gomplate` and/or a local `caddy` (or Docker access) for validation. For local CI, a `caddy` shim or installing the `caddy` binary is a common pattern.

Troubleshooting checklist
-------------------------
- If gomplate fails: run `gomplate -f proxy/Caddyfile.template -o /tmp/rendered_caddyfile` and inspect stderr.
- If caddy adapt fails: run `docker run --rm -i caddy:2 caddy adapt --config - < /tmp/rendered_caddyfile` to get the parser error.
- If deploy fails: ensure the `proxy` compose service is running in the current repo directory and `docker compose ps -q proxy` returns a container id.

Useful quick commands
---------------------
- Render: `gomplate -f proxy/Caddyfile.template -d env -o /tmp/rendered_caddyfile`
- Validate via container: `docker run --rm -i caddy:2 caddy adapt --config - < /tmp/rendered_caddyfile`
- Deploy (repo proxy running): `./scripts/deploy/render_caddy.sh`

Dependencies
------------
Minimum required tools to run the configuration flow and to perform strict validation:

- docker (>= 20.10.0) and Docker Compose (>= 2.0.0)
- gomplate (https://github.com/hairyhenderson/gomplate) — template renderer
- caddy (v2) for `caddy adapt` and `caddy reload` (or Docker access to the `caddy:2` image)
- curl (for smoke tests)

Quick install hints (Debian-based systems)

```bash
# Install docker and compose using the repo's installer or distro packages
sudo apt update
sudo apt install -y docker.io docker-compose-plugin curl

# Install gomplate (example x86_64 Debian/Ubuntu)
sudo curl -sL https://github.com/hairyhenderson/gomplate/releases/latest/download/gomplate_linux_amd64 -o /usr/local/bin/gomplate
sudo chmod +x /usr/local/bin/gomplate

# Option A: install caddy binary (recommended for offline validation)
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo apt-key add -
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy

# Option B: use the dockerized caddy for validation (no install required)
# docker run --rm -i -v /:/host_root caddy:2 caddy adapt --config /host_root/tmp/rendered_caddyfile
```
